Provider Definition.

Cada proveedor tendría tres elementos:

Provider
 ├── connection.yaml
 ├── mapping.yaml
 └── capabilities.yaml
1. connection.yaml

Solo dice cómo hablar con el proveedor.

provider: musescore

base_url:
  https://api.musescore.com

authentication:
  type: bearer

headers:
  Accept: application/json

search_endpoint:
  /v2/search

resource_endpoint:
  /v2/resource/{id}

download_endpoint:
  /v2/download/{id}

Nada más.

No sabe nada de OSAP.

2. mapping.yaml

Aquí está la magia.

Describe cómo convertir el JSON del proveedor al modelo Work.

Ejemplo.

Proveedor devuelve

{
    "composer_name":"Wolfgang Mozart",
    "song_name":"Ave Verum",
    "keysig":"F major"
}

Nuestro modelo necesita

composer
title
musical_key

El mapping dice

work:

  composer:
      source: composer_name

  title:
      source: song_name

  musical_key:
      source: keysig

Otro proveedor podría decir

{
   "author":"Wolfgang Mozart",
   "title":"Ave Verum",
   "key":"F"
}

Su mapping sería

work:

  composer:
      source: author

  title:
      source: title

  musical_key:
      source: key

OSAP nunca cambia.

Incluso listas
metadata:

   instruments:
      source: instruments[*].name

   genres:
      source: genres[*].title
O transformaciones
metadata:

   duration:
      source: duration
      transform: seconds_to_hhmmss
O concatenaciones
catalogue:

    source:
       - opus
       - number

    transform: concat_space
O constantes
provider:

    name:
        constant: musescore
3. capabilities.yaml

Cada proveedor declara qué soporta.

supports:

    lookup: true

    search: true

    resource: true

    download: true

    statistics: false

    metadata: true

    resources: true

Así API sabe automáticamente qué puede pedir.
