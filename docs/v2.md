## Temas a revisar en V2

- **Límite de peticiones** (rate limiting): por IP y/o API Key.
- **Métricas**: ampliar (latencia, errores) si hace falta.
- **Panel de administración**: área separada que consume la API.
- **Completar metadatos**: ~164K entradas sin `composer` (el CSV las trae como NA); backfill
  puntual cuando la fuente las tenga.

## Usuarios (gestión básica)

- **Fichero de usuarios muy básico**, **totalmente encriptado** (no en claro).
- **Límite de ficheros descargados por día** por usuario.
- Si ese fichero/gestión de usuarios es **común a OSAP**, debe exponerse **API** para que OSAP
  lo consulte (no duplicar la gestión).
- Herramientas necesarias:
  - Alta (registro) y baja
  - Cambiar contraseña
  - Confirmación de correo
  - (futuro) Donación / contrato
- Modelo de negocio: la web pasa a ser un **servicio público gratuito**; los costes pueden
  requerir **financiación** (donaciones/contrato) más adelante.

### Autenticación (posible en V2)

Puede activarse acceso por **usuario/contraseña** y **validación externa** (OAuth2/OIDC):

- Login con **Google** (y posiblemente otros proveedores: GitHub, Microsoft...).
- Sesiones/tokens (JWT) emitidos por la API; sin sesiones por proveedor.
- **2FA/MFA** opcional para cuentas que lo requieran.
- El modelo de cuenta debe soportar: estado (activo/inactivo/bloqueado), límite diario de
  descargas y rol (público / administrador).
- El proveedor de identidad externo **nunca** sustituye al fichero de usuarios del sistema:
  la cuenta local sigue existiendo y guarda límites/permisos; OAuth solo valida la identidad.
- Compatible con el requisito de "fichero de usuarios común a OSAP": la API de usuarios
  expone autenticación y consulta sin exponer credenciales.

### Nota de diseño

Hoy **no hay autenticación** (acceso abierto). La activación de login será **opcional** y por
fases: primero API Key (uso/medición), después cuentas locales, después OAuth2/Google.

## Separación de proyectos (responsabilidades claras)

- **Open Music Repository (OMR)** → el servicio público: la web, la API y el almacenamiento
  de partituras. Es el proyecto actual (osap-storage).
- **OSAP** → el **cliente inteligente** que consulta OMR (y, si es necesario, otras fuentes)
  para encontrar y obtener partituras.
- Otras aplicaciones también deben poder consumir OMR sin depender de OSAP.

## Internacionalización (i18n)

- Idiomas: **castellano, catalán, inglés, francés, italiano y alemán** (`es, ca, en, fr, it, de`).
- Ámbito:
  - **Web pública** (landing, buscador, documentación, panel de administración): traducción completa
    con selector de idioma.
  - **API**: respuestas JSON estructuradas y neutras (sin texto localizable embebido); los textos
    legibles se localizan en la web/cliente según `Accept-Language`. Los nombres propios
    (compositor, título) se conservan tal cual.
- Estrategia:
  - Las traducciones viven en la **capa web (cliente de la API)**, nunca en el dominio.
  - Catálogos por idioma (gettext / `translations/{lang}.json`).
  - Detección por `Accept-Language` + selector manual (persistente).
  - URLs por idioma opcional (`/en/`, `/es/`...) o parámetro de idioma.

## Buenas prácticas / principios SOLID

La programación debe seguir buenas costumbres y los **principios SOLID**:

- **S** — Single Responsibility: una clase / un caso de uso hace una sola cosa.
- **O** — Open/Closed: añadir proveedores o tipos sin modificar el dominio (registro de backends,
  `ProviderType`, puertos).
- **L** — Liskov: los adaptadores sustituyen a sus puertos sin cambiar el comportamiento esperado.
- **I** — Interface Segregation: puertos pequeños y específicos (`FileRepository`, `StorageBackend`,
  `FileHasher`, `ArchiveReader`...).
- **D** — Dependency Inversion: el dominio define los contratos; infraestructura y API los implementan;
  las dependencias apuntan hacia el dominio.

Reglas de proyecto: sin lógica de negocio fuera de `domain/` + `application/` + la API; la web/cliente
consume solo la API; sin duplicar código; cobertura de tests para dominio/aplicación.

## Notas de arquitectura (recordatorio)

- La web y el panel consumen **solo la API**; nunca acceso directo a MariaDB ni al dominio.
- El dominio y la lógica de negocio siguen residiendo en `domain/` + `application/` + la API.
- El mirror es el repositorio oficial (R2 en producción); no hay "backends" intercambiables en
  producción.
